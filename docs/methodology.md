# Bridgework — Methodology

Full design rationale lives in the Master Research & Architecture Blueprint
v1.0. This document is the implementation-facing summary.

## Model

Unlevered Free Cash Flow, deterministic, 7 canonical drivers:

```
Revenue        = revenue_prior * (1 + revenue_growth)
Gross Profit   = Revenue * (1 - cogs_pct)
EBIT           = Gross Profit - Revenue * opex_pct
Taxes          = max(EBIT, 0) * tax_rate
NOPAT          = EBIT - Taxes
Delta NWC      = Revenue * nwc_pct - Revenue_prior * nwc_pct
CapEx          = Revenue * capex_pct
FCF            = NOPAT - Delta NWC - CapEx
```

`src/bridgework/model.py` is the single source of truth. Excel workbooks
are a byproduct, regenerated from it — never the reverse.

## Variance attribution

**Sequential bridge** (`variance_bridge.sequential_bridge`,
`all_orderings`) — diagnostic only. Walks V1 → V2 one driver at a time;
full `n!` enumeration for ≤6 changed drivers, seeded 1000-sample estimate
otherwise. Never the headline number, because the result depends on
walk order whenever drivers interact.

**Shapley attribution** (`variance_bridge.shapley_attribution`) — the
primary, order-independent number. For driver *i*:

```
phi_i = sum over subsets S of (other changed drivers) of
            [ |S|! * (n-|S|-1)! / n! ] * ( f(S+{i}) - f(S) )
```

where `f(S)` = model output with drivers in S at their V2 value, all
others at V1. Satisfies Efficiency (sums exactly to total variance),
Symmetry, Dummy, and Additivity (Shapley, 1953). Exact enumeration
(`2^n` coalitions) for `n_changed ≤ 8`; seeded Monte Carlo permutation
sampling above that (Castro, Gómez & Tejada, 2009), with an empirical
95% bootstrap CI and automatic sample-count doubling (up to 3 retries) if
the CI half-width exceeds 2% of |total variance|.

## Interaction diagnostics

Two numbers, both reported, serving different purposes:

- **Net non-additivity** — actual variance minus the sum of isolated
  one-at-a-time impacts. Can partially cancel across driver pairs; this is
  the number Phase 0 originally (and imprecisely) called "the interaction
  effect."
- **L1 non-additivity (ordering-sensitivity exposure)** — the sum of
  absolute **Möbius** interaction coefficients over all subsets of size
  ≥ 2. Never cancels, and it upper-bounds the maximum sequential ordering
  spread. `L1 == 0` if and only if the model is additive over the changed
  drivers, in which case every ordering agrees.

  **Naming, precisely.** This is *not* a model-risk metric. It measures
  the interaction intensity of a given model form **under a specific
  V1→V2 scenario**. A perfectly sound Gordon-growth DCF scores 24.9%
  because the scenario moved two drivers that share a denominator; a
  genuinely broken model scores zero if the scenario never moved the
  broken driver. It is scenario-conditional ordering exposure, and calling
  it "model risk" overstates it.

  **Implementation history worth recording.** An earlier version summed
  absolute *pairwise Grabisch–Roubens indices* and added the three-way term
  only at exactly n=3. That discarded all higher-order terms at n ≥ 4 and
  made the stated invariant false: a four-player game exists whose six
  pairwise indices are all ≈0 (old L1 ≈ 0.002) while every player's
  sequential marginal still swings by 0.278 — wrong by 140×. The Möbius
  formulation has no such hole. Locked by
  `test_l1_captures_higher_order_interaction`.

Pairwise terms use the general Grabisch & Roubens (1999) weighted Shapley
interaction index, not the plain two-driver shortcut
`f({i,j})-f({i})-f({j})+f(∅)` — the two coincide only when the game's
higher-order terms are exactly zero, which the Zoom fixture happens to
satisfy but is not general (verified explicitly in
`tests/test_shapley_axioms.py::test_general_formula_diverges_from_plain_shortcut_when_three_way_nonzero`,
using a fixture that crosses the `MAX(EBIT,0)` tax kink).

## Structural Integrity Analysis (SIA)

8 mechanical, deterministic checks against Bridgework's own controlled
schema (`sia.py`) — not a general-purpose spreadsheet auditor. A failure
halts the pipeline before any attribution runs. See `docs/limitations.md`
for the honest coverage disclosure.

## Excel contract

`schema/excel_contract.md` is the full specification. Ingestion is
constrained round-trip only (Decision 3 in the Blueprint): a workbook must
have been generated by `ingestion.write_excel`, and only the 7 driver
values may be edited before re-ingestion — any other change is rejected
with an itemized error.

## Driver Impact Analysis (DIA) — Phase 2

Answers a **different question** from Shapley, which is why both survive
(Blueprint §C, challenge 2):

- **Shapley** — retrospective/forensic. Attributes a *specific, realized*
  V1→V2 change. "What already happened, and who caused it?"
- **DIA/Sobol** — prospective/risk-scoping. Attributes *output variance*
  under an assumed input distribution around a base case. "What should I
  worry about going forward, even if it hasn't moved yet?"

The distinction is not academic. On this repo's own Zoom fixture,
`cogs_pct` never changed between V1 and V2, so Shapley correctly assigns
it nothing — yet DIA shows it is the **second-largest driver of output
uncertainty** (Sobol ST ≈ 0.17). An analyst reading only the variance
bridge would not know that.

Two methods (`dia.py`):
- **Tornado** (local, one-way): ±20% perturbation per driver, others
  fixed, ranked by |ΔFCF|. Cheap, always available.
- **Sobol** (global, variance-based): first-order `S1` and total-order
  `ST` via SALib. The `interaction_gap = ST − S1` flags
  interaction-concentrated risk.
- **Morris** (optional pre-screen): elementary effects, O(r(k+1)) vs
  Sobol's O(N(2k+2)) — useful before a full Sobol run on a large driver set.

**Input-distribution policy (Assumption #1):** independent uniform ±20%
around each driver's base value. Documented and overridable; not a claim
that ±20% is correct for every driver in every model.

## Threshold & Break-Point Analysis (TBA) — Phase 2

Finds the value of a driver at which a predicate flips (default: FCF
crosses 0), via `scipy.optimize.brentq`.

**Mandatory monotonicity precondition.** Before invoking Brent's method,
TBA scans an 11-point grid and counts sign changes. It proceeds only on
exactly one. Otherwise it refuses explicitly, and — importantly —
distinguishes the two failure modes, because they have opposite fixes:

- **0 sign changes** → the crossing lies *outside* the search range. The
  function may be perfectly monotone. Fix: **widen** the range.
- **≥2 sign changes** → genuinely non-monotone; multiple crossings exist.
  Fix: **narrow** the range to isolate the one of interest.

Conflating these would mislead an analyst into the wrong correction.

**A finding worth recording:** `tests/test_tba.py::test_fcf_is_provably_single_driver_monotone`
verifies that for *this* model, FCF is monotone in every single canonical
driver across its full economically-valid range — including across the
`MAX(EBIT,0)` tax kink — because each driver enters FCF through at most a
two-piece piecewise-linear relationship whose pieces never have
opposite-sign slopes. A genuine "hump" is therefore impossible for a
single-driver TBA sweep here. The guard exists for the general case and
for future richer models, not because this fixture needs it. That is a
deliberate, tested claim rather than an assumption.

## Reporting — Phase 3

`html_report.py` renders a single self-contained HTML document: charts are
base64-embedded, so there are no external asset dependencies and the file
survives being emailed, archived against a close file, or opened offline
in two years.

Everything in it is a pure function of the already-computed
`PipelineResult` — nothing is recomputed, and no narrative, ranking or
estimate is LLM-generated (hard constraint 2). `test_html_is_deterministic_except_timestamp`
locks that in.

**Structure follows the argument, not convention.** A conventional
variance report opens with the headline number and a driver table — which
is precisely the format that creates the problem this tool exists to
solve, by presenting one figure as though it were the only possible
answer. Instead the report opens with the same driver shown three ways
(least-favourable ordering, most-favourable ordering, Shapley), so the
reader understands why an order-independent figure is necessary before
being asked to trust one.

Sections carry audit-workpaper cross-reference letters (A, B, C…) with
tick and exception marks in a left rail. That is genuine audit notation
rather than decoration: the pipeline is a real sequence, and the marks
encode pass/flag status the reader needs.

Phase-2 sections (sensitivity, break points) render only when those stages
ran — no empty shells.

## Cross-company adaptation — Phase 4

The engine computes over seven **canonical driver roles**, never over
company-specific names. A company adapter (`data/<company>/mapping.yaml`)
binds that company's own vocabulary onto those roles:

```yaml
role_map:
  revenue_prior: prior_year_sales_and_revenues   # Caterpillar's own term
  cogs_pct:      cost_of_sales_pct
  opex_pct:      sga_and_rd_pct
```

A driver file then references its adapter with a `mapping:` key and is
written entirely in the company's own language. Files without a `mapping:`
key are assumed already canonical, so the original Zoom files keep working
unchanged.

**The mapping-only rule and how it was actually tested.** The Blueprint
requires that adding a company need zero `.py` changes. Building the
mapping mechanism was itself a one-time change to `ingestion.py` — the
rule cannot be met by a codebase with no mapping layer. So the test was
run properly: the mechanism landed with Caterpillar, that state was
committed, and then a *third* company was added and checked with
`git status --porcelain src/`, which returned empty. Three YAML files, no
source changes.

**Three deliberately different economic shapes:**

| | Gross margin | CapEx intensity | Working capital |
|---|---:|---:|---:|
| Zoom (software) | ~76% | 3.0% | positive |
| Caterpillar (heavy industry) | ~38% | 5.0% | positive |
| Northwind (retail, synthetic) | ~26% | 2.0% | **negative** |

Negative working capital is a real characteristic of grocery retail
(suppliers financed, inventory turns faster than payables come due), and
the Northwind case is additionally engineered so free cash flow crosses
through zero between versions — exercising sign handling across
attribution, charts and the HTML report, which neither real fixture does.

## DCF valuation attribution — Phase 6

The engine never needed to know it was computing free cash flow. It needs
a deterministic function from a frozen driver dataclass to a scalar. Phase
6 makes that explicit: every engine function takes a `model_fn` (defaulting
to `compute_fcf`, so nothing existing changed), and a `ModelSpec` registry
carries the driver vocabulary, Excel layout and output labels the
*pipeline* additionally needs.

**Why a DCF, specifically.** It is the IB and equity-research native
question — "why did our price target move?" — and it is a materially
better demonstration of the attribution problem, because a DCF is severely
non-linear where the FCF model is nearly bilinear. Terminal value is

```
TV = FCF₅ × (1 + g) / (WACC − g)
```

so WACC and terminal growth interact through a *difference in a
denominator*. Measured on the shipped fixture:

| | Zoom FCF | DCF valuation |
|---|---:|---:|
| L1 non-additivity | 9.9% of change | **22.7% of change** |
| Dominant interacting pair | revenue × opex | **WACC × terminal growth** |
| Widest sequential ordering range | $3.86M on a $38.96M move | **$8.12/share on a $45.11 move** |

The WACC × terminal-growth term alone is over half of total pairwise
interaction. On a stock priced near $110, walking the drivers in a
different order changes WACC's credited impact by $8.12 per share. That is
not a rounding argument.

**The coalition-validity guard.** Shapley evaluates every *coalition* —
every mix of V1 and V2 values — so a coalition can pair V1's WACC with
V2's terminal growth and produce `WACC ≤ g`, an undefined model, even
when V1 and V2 are each perfectly valid alone. `dcf.py` raises
`InvalidDCFError` rather than returning a negative-denominator terminal
value, and SIA catches the same condition at the structural gate. The
checkable precondition before comparing two versions is:

```
min(WACC across both versions) > max(terminal growth across both versions)
```

This is the same design philosophy as the TBA monotonicity guard: refuse
explicitly rather than return confident nonsense.

**Scope honesty.** Adding a *company* is a mapping-only change (three YAML
files, zero source changes — Phase 4). Adding a *model* is not: it needs a
compute function and an Excel contract, so it is a code change by nature.
The registry keeps that change contained to one new module plus one entry.

Forecast horizon (5 years) is a fixed model constant, not a driver: it is
an integer and would not behave sensibly under coalition enumeration or
continuous sensitivity perturbation.
